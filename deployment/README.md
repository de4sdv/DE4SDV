# Public deployment: model API and Ask-model viewer

## DE4SDV Experimental Read-Only Systems Modeling API

This directory contains the complete, reproducible deployment for serving the
validated DE4SDV full-model SysML v2 baseline through the standard Systems
Modeling REST/HTTP API at `https://sysml-api.de4sdv.org`.

See [ADR 0013](../docs/architecture-decisions/0013-deploy-experimental-readonly-public-sysml-api.md)
for the decision, the fail-closed rules, and the standards follow-ups.

The same host serves the bounded interactive model viewer at
`https://viewer.de4sdv.org`. See
[ADR 0016](../docs/architecture-decisions/0016-publish-bounded-public-ask-viewer.md)
for the separate application/model identity contract and abuse controls.

## What is served

- The pinned pilot Systems Modeling API implementation
  (Systems-Modeling/SysML-v2-API-Services `0af711b1`), the same revision the
  privileged DE4SDV full-model workflow validates.
- One exact validated Git revision of the DE4SDV baseline, imported into this
  deployment's own API repository through the existing validated import path.
  Element UUIDs from the official Syside export are preserved; the
  Project/Commit UUIDs are generated by the deployment repository (the
  privileged CI run's ephemeral UUIDs are not reused).
- Swagger/OpenAPI documentation from the implementation at `/docs`.
- A machine-readable status document at `/deployment-status.json` with the
  served Git SHA, the deployment-specific SysML project/commit UUIDs, the
  semantic-authority identity (`baseline.semantic_authority`, `sai-…`), the
  served model (`baseline.served_model`: export digest, element count and
  content digest), deployment timestamp, and read-only/experimental status.
  `scripts/verify_public_api.py` checks both with a strict shape.

## What is blocked (by design)

- Everything except GET/HEAD/OPTIONS → rejected 405 at the reverse proxy,
  including unknown/extension methods (positive allowlist).
- Any direct network path to the API or PostgreSQL (no published ports).
- Remote MCP endpoints (MCP stays stdio; clone the repo and point it here).

## First deployment — required sequence

The first public deployment must use a **Git SHA on `main` that contains these
deployment files**. Do not deploy any pre-#176 SHA (for example `85a54b9…`):
that revision predates the deployment implementation.

1. Merge PR #176 → obtain the resulting `main` SHA.
2. Run `Privileged Full-Model API Ingestion` for that exact `main` SHA; it
   must complete green and upload `full-model-api-ingestion-<sha>`.
3. Provision the host (one-time):
   - Create the Cloudflare DNS record (DNS-only, not proxied, so Let's
     Encrypt HTTP-01 works):
     `sysml-api.de4sdv.org. IN A <SERVER-IPv4>`
   - As root on the server:
     `ACME_EMAIL=<email> bash deployment/scripts/provision-server.sh`
   - Set GitHub secrets `DEPLOY_SSH_KEY`, `DEPLOY_SSH_HOST`, `DEPLOY_SSH_USER`,
     and `DEPLOY_SSH_KNOWN_HOSTS` (environment `sysml-api-production`).
4. Run `Deploy Public SysML API` (manual `workflow_dispatch`) with that exact
   main SHA. The workflow independently verifies the privileged run metadata
   (workflow file, `success`, `head_sha` equality, unambiguous selection),
   creates and verifies a Git bundle from the runner's canonical exact-SHA
   checkout, transfers it through the pinned SSH channel, clones it into a
   real exact Git checkout on the host, transfers the validated ingestion
   bundle, and runs `deploy.py` — which imports the validated export into the
   deployment's own API repository, requires 0 unresolved / 0 ambiguous
   ontology mappings, writes the deployment-specific binding, and only then
   exposes the proxy.
5. The workflow always runs external public verification; it cannot be
   skipped. It proves HTTPS, the strict method allowlist (including a
   nonstandard method), the status document, the deployment-specific
   project/commit, the known element by API UUID, and >50k-element
   pagination.
6. Publish/record the resulting deployment-specific API tuple from
   `https://sysml-api.de4sdv.org/deployment-status.json`.

## Availability guarantee (honest wording)

This is a single-host compose stack without a blue/green switch. Every
deployment (including a redeploy) follows this fail-closed sequence:

```text
stop public Caddy
  -> start/restart postgres + sysml2-api
  -> import exact validated export
  -> deployment-specific semantic validation
  -> write deployment-status.json
  -> start Caddy
```

Caddy is stopped FIRST and is only started again after the new
deployment-status.json has been published. If the import or validation
fails, Caddy stays stopped: a partially validated baseline is never publicly
reachable, and a stale status document is never served. The cost is downtime
for the import window; treat deployments as short planned maintenance
windows. This downtime is an explicitly accepted property of the
single-host design, not an accidental gap.

## SSH host-key verification (out of band)

The workflow does NOT trust `ssh-keyscan`. The host key must be established
out of band by the repository owner:

1. After first boot, log in via the Hetzner console (or the first SSH attempt
   from a trusted machine) and read the host's public keys:
   `for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keyscan -t ed25519,rsa <host> 2>/dev/null | head; done`
   or simpler: from your trusted machine run `ssh-keyscan -H <host>` ONCE,
   visually verify the fingerprint against the Hetzner console/recovery
   view, and store the lines.
2. Put those lines into the `DEPLOY_SSH_KNOWN_HOSTS` secret.
3. The workflow writes them verbatim to `known_hosts` and connects with
   `StrictHostKeyChecking=yes`: any mismatch aborts the deployment.
4. Re-verify the key after any server rebuild/recreation and update the
   secret.

## Restart persistence and stale data

- `restart: unless-stopped` on all services plus the `create-drop` → `update`
  schema patch means the service survives reboots without losing the imported
  model. Schema creation happens once; committed model data is never dropped.
- Each deployment stages its bundle into a freshly recreated
  `/srv/de4sdv/artifacts/incoming` (previous artifacts removed first) and the
  host checkout is freshly cloned from the checksum-verified Git bundle,
  `git reset --hard` + `git clean -ffd` at the exact SHA, so no stale files or
  artifacts from previous deployments can leak in. The host does not fetch
  source from GitHub; this avoids making production correctness depend on
  anonymous Git smart-HTTP behavior while retaining a real Git checkout and
  the canonical repository URL as `origin`.

## Secrets hygiene

- DB password and Play secret: generated on the host, stored in
  `${DEPLOY_DIR}/sysml2-api.env` (0600), never in git, never in images.
- GitHub side: `DEPLOY_SSH_KEY` / `DEPLOY_SSH_HOST` / `DEPLOY_SSH_USER` /
  `DEPLOY_SSH_KNOWN_HOSTS` secrets are needed; the SSH key is written 0600,
  never printed, and deleted after every run; the host key comes from the
  out-of-band `DEPLOY_SSH_KNOWN_HOSTS` secret (see above), never from
  dynamic discovery. The Syside license never touches the deployment host
  (exports are produced in the privileged GitHub workflow).
- The status document contains no secrets and no internal paths.

## Ask-model deployment

The Ask-model service is a separate manual deployment. It does not ingest or
copy the model. It mounts the current deployment binding read-only and queries
the model API over the internal container network.

Before the first run:

1. Confirm the native Pages mirror works at
   `https://de4sdv.github.io/DE4SDV/`, then remove `viewer.de4sdv.org` as the
   GitHub Pages custom domain.
2. Move the DNS-only `A` record for `viewer.de4sdv.org` to the existing
   deployment host. This is a controlled cutover: DNS cannot route only
   `/ask`. Keep the previous Pages DNS target recorded for manual reversal.
3. Add `NOUS_API_KEY` to the protected `sysml-api-production` GitHub
   environment. The workflow transfers it through the pinned SSH channel into
   `/srv/de4sdv/ask-viewer.env` with mode `0600`; it is never committed or sent
   to the browser.
4. Merge the reviewed deployment change and run **Deploy Public Viewer with
   Ask-model** with that exact `main` SHA. The production environment approval is
   mandatory.

The workflow requires DNS to resolve to the deployment host, transfers an
exact Git bundle, starts the internal Ask container, waits for semantic warmup,
validates the proxy configuration, and then recreates the proxy. External
verification makes exactly one paid query after checking identity and policy.
On host-side failure, the workflow restores the previous checkout and proxy.
Because DNS is outside that transaction, restoring the former public Pages
route also requires manually restoring its custom-domain setting and DNS
target. The native Pages URL remains available throughout.

Public controls are deliberately tighter than the read-only model API: three
Ask requests per remote host per minute, sixty globally per hour, one hundred
twenty globally per day, one active inference call, a 16 KiB body limit, and
exact same-origin enforcement. The scheduled monitor is GET-only and does not
consume inference quota. These are abuse controls and a daily request ceiling,
not an exact monetary guarantee. Monitor inference usage and stop the Ask
service if traffic or cost becomes abnormal.

### DE4SDV Guide (`/api/repo-chat`)

The same viewer container also serves **DE4SDV Guide**, the repository
assistant: a separate capability from Ask the model, on its own endpoint
`POST /api/repo-chat` (`tools/sysml_html_viewer/repo_guide.py`). It
answers newcomer questions about the Git repository — documentation,
ADRs, tooling, contribution workflow — grounded in the **exact deployed
checkout** through a deterministic SQLite FTS5 retrieval index built
lazily by the server (no vector database). The index excludes `.git`,
secrets/environment files, build output, caches, and generated assets;
retrieval is keyed to the checkout's HEAD, so the index rebuilds when the
deployment moves to a new SHA. Source references in answers are GitHub
links pinned to the deployed application SHA.

Authority boundary (also stated in the UI and the viewer README):
DE4SDV Guide is a **generated** repository/documentation assistant, not
an engineering or model authority; it never queries the Systems Modeling
API and never falls back to Ask the model (nor the reverse). When no
trustworthy repository context matches a question, the endpoint returns
404 and the guide says it cannot answer rather than guessing. The proxy
route mirrors the `/ask` hardening — POST-only, same 16 KiB body limit,
and an independent rate-limit budget (`guide_global`, `guide_daily`,
`guide_per_ip`) so the two capabilities can never consume each other's
hourly/daily spend. No server-side user memory or accounts exist in V1;
conversation state is browser-local.

## Runtime contract

The Ask viewer and the semantic MCP server start from four things and
nothing else (owner decision 2026-10-11: the model-authority bundle, closure
and activation ceremony is retired):

1. **A clean checkout of the deployed commit.** On the host,
   `/srv/de4sdv/DE4SDV`, mounted read-only into the ask-viewer. The
   ask-viewer image holds only the Python runtime: its entry point and the
   viewer run from this checkout. `deploy.py` builds the image before it
   stops the proxy, so a Dockerfile change takes effect and a failed build
   changes nothing.
2. **The deployment binding.** `/srv/de4sdv/artifacts/current/de4sdv-full-model-binding.json`,
   written by this deploy's own import: a revision binding v2 with the
   ingestion-validated kernel bindings (ADR 0011) and the `served_model`
   record. That record names the validated export (file digest), its element
   count and its content digest. The importer writes it only after the
   full-payload read-back found every element of the API listing equal to the
   export (schema padding without a value is ignored; numbers compare by value).
3. **The deployed API.** `http://sysml2-api:9000` inside the compose network.
4. **One startup check** (`de4sdv/semantic/deployment_runtime.py`). It
   refuses unless all of these hold:
   - **right commit:** the checkout HEAD is the deployed commit, the binding
     is a passed full-model binding of the expected model revision, and the
     application revision descends from it;
   - **clean tree:** `git status --porcelain` is empty;
   - **same semantic authority:** the `sai-` identity recomputed from the
     checkout equals the binding's. It is computed from the contract data in
     `de4sdv/semantic/contract-data/`, file paths included;
   - **served model = validated export:** the binding records the served
     model, and no corpus is used unless its content digest is exactly that
     record's. This part runs when the corpus loads (the warm-up). A snapshot
     that is not the export is ignored; an API corpus that is not the export
     is refused, and every semantic answer is refused with it.

Environment. The ask-viewer needs `DE4SDV_APP_GIT_SHA` (the deployed commit;
`deploy.py` and the Ask deploy workflow set it); the binding path and API URL
are fixed in `compose.yaml`. The MCP server takes `--api-url`, `--binding` and
`--expected-git-revision` (or `DE4SDV_SYSML_API_URL`, `DE4SDV_REVISION_BINDING`
and `DE4SDV_EXPECTED_GIT_SHA`) and runs from a clean checkout of that commit.
There is no authority selector and no bundle variable: compose no longer
reads `DE4SDV_SEMANTIC_AUTHORITY` or `DE4SDV_MODEL_AUTHORITY_BUNDLE[_ID]`.

Refusal is loud. A refused startup makes `/ask-status.json` report
`semantic_authority.kind == "invalid"` with the reason, and the viewer then
answers only on the labeled regex path. The MCP server exits with status 2
and does not start. `/ask-status.json` reports `startup_check`, the served
`semantic_authority` (`sai-…`), `served_model` and `served_model_check`. The
post-deploy verifier (`verify_public_api.py`), the Ask verifier
(`verify_public_ask.py`) and the scheduled monitor (`monitor_public_ask.py`)
compare them with `deployment-status.json`. Nothing is declared by hand.

## Release

Three commands. The only owner gate is the `sysml-api-production` approval.

```bash
# 1. Privileged run at the exact main tip (licensed export, CI import
#    rehearsal with the three batteries, release evidence over the export).
gh workflow run privileged-full-model-api-ingestion.yml --repo de4sdv/DE4SDV \
  --ref main -f ref=<SHA>

# 2. Deploy that SHA; approve sysml-api-production when GitHub asks. The
#    verifier waits for the Ask warm-up and its served-model check.
gh workflow run deploy-public-sysml-api.yml --repo de4sdv/DE4SDV \
  --ref main -f git_sha=<SHA>

# 3. Re-point the agents' MCP server: the byte-exact deployment binding and
#    a clean checkout of <SHA>; then restart the agent sessions.
scp deploy@<host>:/srv/de4sdv/artifacts/current/de4sdv-full-model-binding.json \
  ~/.hermes/de4sdv-semantic/binding.json && \
  git -C ~/.hermes/de4sdv-semantic-worktree checkout --detach <SHA>
```

Agents set `DE4SDV_EXPECTED_GIT_SHA=<SHA>` and drop any
`DE4SDV_SEMANTIC_AUTHORITY` or `DE4SDV_MODEL_AUTHORITY_*` entries from their
MCP configuration. Step 1 must finish green: the deploy refuses a SHA without a
successful privileged run. `scripts/check_release_evidence.py` is that run's
release gate: revision, export digest, served model, binding and kernel
bindings, the runtime answers over the export (K pair, EvidenceContract
closure, VerificationCase grounding), coverage and the battery identities.

After the deploy succeeds, add the release to the
[production-release table](../configuration-management/baseline-register.md#production-releases)
of the baseline register in a pull request.

The CI import rehearsal in step 1 was planned to stop two releases after the
ceremony retirement. It still runs, because the successor parity's API half
needs the import. It includes the full import, two candidate imports,
correspondence, pilot read-back and the three API batteries. Four releases ran
under this contract from 2026-10-15 to 2026-10-21. Step 1 took 2 h 32 min to
3 h 43 min. Step 2 took 50 to 60 minutes after the approval. Before the
contract, step 1 took 4 h 9 min in
[run 38095581274](https://github.com/de4sdv/DE4SDV/actions/runs/38095581274).
Its retained slow steps took 11,705 seconds (about 195 minutes).

During the first two releases after the retirement, leave the 063c4fb1 lines in
`/srv/de4sdv/sysml2-api.env` (`DE4SDV_SEMANTIC_AUTHORITY`,
`DE4SDV_MODEL_AUTHORITY_BUNDLE`, `DE4SDV_MODEL_AUTHORITY_BUNDLE_ID`) and the
bundle under `/srv/de4sdv/artifacts/model/` in place. Current compose ignores
them, and the rollback below needs them.

## Rollback

Rollback is a redeploy of the previous release. The release before the
ceremony retirement is `063c4fb1f2763a366874118f3b78d9841e0d11b4` (bundle
`mab-32da05b896fee9d5a47874e7f305f741`, privileged run `38095581274`). It needs
its own workflow definition and verifier, so dispatch it from the
`release-2026-10-11` tag. Main's deploy workflows refuse that revision before
any host change.

Before step 1, set `ARTIFACT_RUN_ID=38095581274` only while its
`full-model-api-ingestion-063c4fb1f2763a366874118f3b78d9841e0d11b4` artifact
is unexpired. Use the same verified run ID for redeploy and R5. After expiry,
obtain a fresh run as described below; the local archive alone does not
satisfy either command's provider checks.

```bash
# 0. Once, before it is needed (a repository write: Orkun).
git tag -a release-2026-10-11 063c4fb1f2763a366874118f3b78d9841e0d11b4 -m "method release: production at 063c4fb1" && git push origin release-2026-10-11

# 1. Redeploy 063c4fb1 with its own workflow; approve sysml-api-production.
: "${ARTIFACT_RUN_ID:?set to a successful run with an unexpired exact-SHA artifact}"
gh workflow run deploy-public-sysml-api.yml --repo de4sdv/DE4SDV --ref release-2026-10-11 \
  -f git_sha=063c4fb1f2763a366874118f3b78d9841e0d11b4 -f artifact_run_id="$ARTIFACT_RUN_ID" \
  -f expected_semantic_authority=mab-32da05b896fee9d5a47874e7f305f741

# 2. Re-close its bundle at the new deployment binding (the redeploy minted new
#    project/commit UUIDs, so the earlier deployment-bound closure no longer fits).
~/release/r5-closure.sh 063c4fb1f2763a366874118f3b78d9841e0d11b4 "$ARTIFACT_RUN_ID" \
  mab-32da05b896fee9d5a47874e7f305f741 --apply

# 3. Install the re-closed bundle and recreate only the ask-viewer.
~/release/r6-activate.sh 063c4fb1f2763a366874118f3b78d9841e0d11b4 \
  mab-32da05b896fee9d5a47874e7f305f741 \
  ~/release/work/063c4fb1f276/r5/out/closed/de4sdv-model-authority-bundle.json --apply
```

This is the R4→R5→R6 sequence that activated 063c4fb1 on 2026-10-11 (each
release-kit script runs as a dry run without `--apply` first; agents re-point
with `~/release/r7-agent-rebind.md`). It takes about 2.5 hours. Between steps 1 and 3 the Ask viewer answers only on
the labeled regex path. Run 38095581274's full-model ingestion artifact expires
on 2026-10-25T02:52:40Z. After that, before step 1, Orkun dispatches a fresh
privileged run using the old workflow at the rollback tag:

```bash
gh workflow run privileged-full-model-api-ingestion.yml --repo de4sdv/DE4SDV \
  --ref release-2026-10-11 -f ref=063c4fb1f2763a366874118f3b78d9841e0d11b4
# After completion and evidence review:
ARTIFACT_RUN_ID=<new-successful-run-id>
```

Verify the run checked out the exact old SHA, `ingest-and-validate` succeeded,
and the exact-SHA ingestion artifact exists once and is unexpired. Then run
steps 1–3 with that run ID. R5 validates and downloads that provider artifact;
it has no archive-consumption option. Keep `~/release/archive/063c4fb1/` for
recovery and diagnosis, not as an undocumented replacement for its download.
The fresh run's duration is not guaranteed by the historical estimate.

After the second release under this contract, the previous release is itself
a contract release, and its rollback is step 1 alone (`--ref main`, no bundle).

The separate Ask deployment refuses pre-retirement revisions before SSH
setup. Its failure rollback runs only after activation was attempted and
requires the exact run-attempt backup and promotion marker to match the
requested SHA. Refusal, an unrelated backup or a foreign live revision cannot
authorize it to replace the source or recreate Ask/Caddy. Success cleanup
likewise removes only that attempt's owned recovery material.
Before failure rollback mutates source or invokes Compose, the owned backup
must resolve to a Git commit and contain the required Compose file. A damaged
backup is retained for diagnosis without replacing the valid live checkout.

## Known limitations

- The pilot implementation serializes large result sets server-side; complete
  model pagination is expensive upstream (measured during PR #174). Rate
  limiting bounds abuse; the real fix is upstream QueryService work (ADR 0013
  follow-ups).
- One isolated API project per imported baseline; chronological commits within
  a persistent project is a documented follow-up.
- Single-host availability model as described above.
