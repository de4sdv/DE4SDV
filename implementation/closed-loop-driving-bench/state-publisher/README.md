# statePublisher (INC-DRIVING-001, slice 10b, S1)

The operational-state publisher of the closed-loop driving bench: it takes the
agent's plan, ego-motion sample and mode and the actuation adapter's actuation
state over S-CORE mw::com, and publishes the bench's operational state —
`plan`, `vehicle_state`, `health` — as three `PreSerializedData<2048>` events
for gatewayd, which maps them to the SOME/IP service `0x4DF0` / `0x0001`
(events `0x8001`–`0x8003`) and translates them into the typed
`de4sdv.driving.v1.DrivingOperationalState` topic (REFLECTION mode).

Contract: [`../interfaces/ICD.md`](../interfaces/ICD.md) v2, sections 1, 2, 3
and 6. Model authority: `closedLoopDrivingPhysicalSystem.linuxHost`
`.drivingSoftware.statePublisherApplication` in
`textual-notation-of-model/packages/features/driving/closed_loop_driving_physical_software_realization.sysml`,
with MAP-DRIVING-OPERATIONAL-STATE, MAP-DRIVING-MODE and
MAP-DRIVING-ACTUATION-STATE. Requirements: REQ-DRIVING-015 to -019, -029,
-035.

There is no protobuf in this component. The wire format is the ICD v2 §3
SOME/IP struct: 43 fields in table order, big-endian, no struct length field,
AUTOSAR UTF8 strings and dynamic float arrays.

## The encoding (ICD v2 §3)

One `DrivingOperationalState` per event, fields 1..43 always written in table
order, so the layout is fixed and a decoder can walk it without tags:

- `u32` — 4 bytes, big-endian.
- `f32` — IEEE 754 binary32, 4 bytes big-endian (NaN, ±Inf and −0.0 pass
  through unchanged).
- `str` — a 4-byte big-endian byte count covering BOM + bytes + NUL, then
  `EF BB BF`, the UTF8 bytes, `00`. An empty string is therefore **8 bytes**
  (length 4 + BOM + NUL), not 4.
- `f32[]` — a 4-byte big-endian length **in bytes**, then the elements. An empty
  array is a 4-byte zero.
- Fields of the other kinds are zero, `""` or `[]` as their type dictates.

Frame layout stays the P4 probe's: `PreSerializedData<2048>` with the 32-bit
little-endian message length in bytes 0–3 (bytes 0–1 carry it; 2–3 are zero
because a message is under 64 KiB) and the struct from byte 4. `size = 4 +
message_length`; the oversize guard drops anything over 2044 bytes and counts
it in `dropped_samples`.

Measured sizes (message / frame):

| vector | bytes | what it holds |
|---|---|---|
| `health_priming` | 218 / 222 | all-defaults health |
| `plan_full` | 1298 / 1302 | 64 samples, standard ids |
| `plan_max_strings` | **1390 / 1394** | 64 samples, all three ids at the payload's 63-byte limit — the worst case |
| `plan_short` | 288 / 292 | 3 samples |
| `plan_empty` | 274 / 278 | 0 samples: four zero-length arrays |
| `plan_unicode` | 1301 / 1305 | UTF8 ids |
| `plan_random` | 1286 / 1290 | 256 pseudo-random f32 values |
| `vehicle_state` | 218 / 222 | one motion sample |
| `health_stop_*` | 231–234 | stop health |
| `health_refusal` | 367 / 371 | 64-char SHA-256 pair + reason |

The worst case is 654 bytes under the budget. `DrivingPlanPayload`'s ids are
`char[64]` (63 bytes + NUL), which bounds every string on the wire; the message
cannot reach 2044 with a well-formed payload, so the oversize path is a guard,
exercised through `Options::messageCapacityBytes` (lowered in the tests).

## The wire fields

| # | source |
|---|---|
| 1–2 | `schema_major` 2, `schema_minor` 0 |
| 3–4 | kind (1/2/3), per-kind sequence from 1 |
| 5 | `"statePublisher"` |
| 6–9 | publish time: real and monotonic as `(s, ns)` |
| 10 | `plan.frameIndex` |
| 11 | `plan.frameIndex × 100` (ICD §1), cross-checked against `captureTime` |
| 12–13 | `plan.productionTime` split |
| 14–15 | `plan.planReference`, `plan.runRecord` |
| 16 | `plan.producer` (`drivingAgent/inferPlan`) |
| 17 | number of samples actually carried (≤ 64) |
| 18 | `plan.horizon` |
| 19–22 | `acceleration`, `curvature`, `x`, `y` of the 64 samples |
| 23–26 | `sample.speed`, `.longitudinalAcceleration`, `.lateralAcceleration`, `.yawRate` |
| 27 | `llround(sample.captureTime × 1000)` — the payload has no frame index |
| 28–29 | receipt time split |
| 30–31 | reported mode, cause (first stop cause latched) |
| 32 | `superviseLoop`, `actuationAdapter`, or `""` while starting |
| 33–34 | cause-since: the mode's `decisionTime`, or the adapter's `stopSinceMono` |
| 35–39 | last plan frame index, its capture ms, newest step capture ms, its production time |
| 40 | publisher-side drops so far |
| 41–43 | refusal detail from `SetRefusal(expectedSha, actualSha, reason)` |

**Time splits.** `SplitSeconds(x)` is `llround(x × 1e9)` split into `(s, ns)`,
so `.9999999996` s becomes `(1, 0)` and `ns` is always in `[0, 999999999]`;
non-finite or negative input is `(0, 0)` and a time past 2^32−1 s saturates.
Real time is **not** computed as a double sum: `SetRealTimeAtMono` stores one
integer nanosecond offset and every publication is `mono_ns + offset_ns`, so
the nanoseconds do not wobble with the ~238 ns resolution of a double at
1.7 × 10⁹ s (a double sum moved a `_ns` field by 128 ns in testing).

**Simulation ms.** `SimulationMs(x)` is `llround(x × 1000)`. For a plan the
frame index wins (ICD §1: frame × 100 is exact) and a disagreement with
`captureTime` is logged once as `error {code: capture_time_mismatch}`; for an
ego-motion sample there is no frame index and the rounded capture time is used.

## Design notes

**Where the decisions live.** The shell owns no policy: it stamps the receipt
time once per sample, calls one `PublisherCore` method, sends the returned
frames and writes the returned log records. The health period, the stop latch,
the sequence numbers, the clamping and the encoder are in the library, which is
unit-tested without S-CORE.

**Clock injection.** `PublisherCore` reads no clock. `Tick(now_mono)` and the
`receipt_mono` argument of each input are the only time source, so the tests
drive a simulated monotonic clock exactly. `CLOCK_REALTIME` is paired once with
`SetRealTimeAtMono(mono, real)`; chrony keeps that offset constant on the host
(ICD §1), so it is not re-sampled per message.

**Health schedule.** The first call of any kind emits a priming health at once
and starts the schedule; then a health every 100 ms of monotonic time
(REQ-DRIVING-017 allows 200 ms, 100 ms leaves margin), whether or not inputs
arrive. After a stall the next call publishes **one** health and skips the
deadlines that passed, rather than replaying duplicates with the same
timestamp. An immediate health is published in the same call that latches the
stop, and again when the agent's mode advances `kStopResponse → kStandstill`
(more frequent than required, which the contract allows).

**Stop latch.** The first report of a stop wins and is latched for the rest of
the run: mode `kStopResponse`/`kStandstill`/`kRefused` from the agent
(`mode_source = "superviseLoop"`) or `stopInForce` from the adapter
(`mode_source = "actuationAdapter"`, reported mode `kStopResponse`). The cause
and `cause_since` are kept from that first report; nothing clears the stop.
A stop the **agent** named follows the agent's own mode onwards (to
`kStandstill`, which publishes one more health and logs
`stop_response.standstill`); a stop the **adapter** named keeps its mode, cause
and instant, so `mode_source` always names the report that began the stop.
`stop_response.begin` and `stop_response.standstill` go to the log with the
cause (ICD §6).

**Sequences.** Per kind, from 1, no gaps: a message that cannot be built
(oversize) consumes no sequence number and only increments `dropped_samples`,
which the next health carries. A downstream failure (`Allocate` or `Send` in
the shell) counts in the same counter through `NoteDownstreamDrop`.

**Refusal.** `SetRefusal(expectedSha, actualSha, reason)` is a setter: the
detail rides the next health (≤ 100 ms, or the immediate health of the
`kRefused` stop), so call it as soon as the refusal is known. Values longer than
the contract (64 bytes per SHA, 32 for the reason) are cut and the cut is
logged as `error {code: refusal_detail_truncated}` — no detail disappears
silently.

**Log (ICD §6).** Every crossing is a record: `in.plan`, `in.mode`,
`in.ego_motion_sample`, `in.actuation_state` with the full payload (samples
included, enums by name), `out.operational_state` with the message as sent
(`seq` is the per-kind sequence, `data.kind` says which event), plus `start`,
`ready`, `config`, `error`, `drop`, `stop_response.begin`,
`stop_response.standstill` and `stop`. Payload time fields keep their model
names and a sibling `clocks` object names each one's clock
(`{"capture_time": "simulation", "production_time": "monotonic"}`); times this
process stamps carry the suffix (`receipt_time_mono_ns`, `publish_mono_ns`,
`publish_real_ns`, `plan_capture_sim_ms`, `step_capture_sim_ms`,
`cause_since_mono_ns`). Non-finite floats are JSON `null`.

**Non-blocking.** The shell polls every 2 ms with `GetNewSamples(..., 8)` and
never waits on a producer or on the gateway; a full slot is a dropped sample
counted by mw::com itself. The publisher sends nothing back to the agent or the
adapter (REQ-DRIVING-018, -019) — it has no port into them.

## Tests

1. **C++ core** (`tests/test_publisher_core.cpp`, 2396 checks): framing and the
   fixed big-endian layout with hand-computed offsets, message sizes, the time
   splits (carry, saturation, nanosecond bound), the health period, per-kind
   sequences, the stop latch and its provenance, `stopSinceMono`, fields 35–40,
   the refusal fields (including truncation), the plan/step capture check, the
   oversize and tiny-capacity paths. Timing semantics are unchanged from the
   accepted v1 core.
2. **Independent decoder** (`tests/decode_vectors.py`, 2467 checks): parses the
   43-field table out of `ICD.md` (names, order, types) and the encoding rules
   from §3, decodes all 16 vectors, asserts every field against the dumper's
   input intent, checks the hand-written key values (capture ms, UTF8 texts,
   refusal SHAs, stop instants), and reports sizes. It never reads
   `publisher_core.cpp`.
3. **Property test** (`plan_random`): 256 pseudo-random f32 values per vector,
   re-derived in Python from the same LCG, must round-trip bit-exactly, and the
   decoded values must re-encode to the exact bytes on the wire.
4. **Time-split carry**: `health_time_carry` publishes at 5.9999999996 s and
   must come out as `(6, 0)`; the C++ test also covers `.9999999994` (stays
   `999999999`) and saturation.

`tests/vectors/expected.json` holds the fully decoded 43 fields of every
vector (plus the field order, the types and the message size), for
cross-checking a decoder written elsewhere. Non-finite floats and negative zero
are the tokens `"NaN"`, `"Infinity"`, `"-Infinity"`, `"-0"`.

## Untested here, must be confirmed on the first build

The shell compiles against nothing real on this machine. It is only
syntax-checked against `tests/mock`, so the following assumptions are untested:

1. **Proxy API.** `AsProxy<Interface>` takes a template-template parameter (as
   `AsSkeleton` does in the P4/P5 probes). `Proxy::StartFindService(handler,
   specifier)` with `handler(ServiceHandleContainer<HandleType>,
   FindServiceHandle)`, `Proxy::Create(handle)`, `proxy.Subscribe(max_count)`
   and `proxy.GetNewSamples(fn, max)` where `fn` receives a `SamplePtr<T>`.
   **The P4/P5 reference sources only show the skeleton side** — this is the
   highest-risk area of the shell.
2. `RuntimeConfiguration{std::string path}` and `InitializeRuntime`, and the
   behaviour when the configuration is not passed (`--mw-com-config` absent).
3. `PreSerializedData::data` is a byte array and `::size` a `std::size_t`
   (copied from P4, so likely right).
4. That `OfferService()` succeeds before the first `Tick`, and whether gatewayd
   (one subscriber) needs the offer before it starts.
5. Timing: whether a 2 ms poll inside a 100 ms budget holds on the G4 with the
   plan, mode, sample and actuation callbacks in one thread. If it does not, the
   library is unaffected — only the shell's loop changes.
6. `startFindService` lifetime: the handle `findHandle_` is kept but
   `StopFindService` is not called; the process ends anyway.
7. The mw::com config's service ids 7401–7406 are the ICD §2 values; that the
   installed S-CORE accepts ids in that range (and the SHM binding) is a P1
   build fact.
8. That gatewayd's REFLECTION `type_definition` maps this struct to the typed
   topic (S4's observer checks it); nothing here can test the broker.

## ICD v2 problems found, with proposed fixes

1. **`sample_capture_ms` has no frame index.** `EgoMotionSamplePayload` carries
   `captureTime` in seconds and nothing else; §3 field 27 wants simulation ms.
   The publisher rounds `llround(captureTime × 1000)`, which is exact for the
   contract's 100 ms grid but off by up to 0.5 ms if a producer ever sends a
   time between grid points. *Proposed change:* add `std::uint64_t frameIndex`
   to `EgoMotionSamplePayload` (the agent has it) and let field 27 be
   `frameIndex × 100`, as field 11 is for the plan.
2. **Field 37 (`step_capture_ms`) does not say which steps.** "The newest step
   the publisher saw" can mean the newest ego-motion step or the newest of
   either input. Implemented as `max` over plan capture ms and sample capture
   ms. *Proposed wording:* "the greatest simulation ms seen in any plan or
   ego-motion sample".
3. **Field 33 for the adapter's stop is ambiguous.** §4 dates the adapter's
   timeout "from the actuation time of the last valid one", while §3 says
   `cause_since` is "when the stop began". Implemented as the instant in
   `ActuationStatePayload.stopSinceMono`, i.e. when the stop began, not when the
   first stop sample happened to be published. *Proposed wording:* "for
   `actuationAdapter`, the monotonic instant of the last valid actuation, not
   the publish time of the stop sample".
4. **Field 17 is not defined for a malformed plan.** "64 when well-formed"
   leaves a `sampleCount > 64` plan undefined; the payload only holds 64
   samples, so the publisher clamps the arrays and publishes the carried count
   (≤ 64). A malformed plan is therefore indistinguishable from a full one on
   the wire. *Proposed wording:* "the number of samples carried (≤ 64);
   REQ-DRIVING-027 judges the reported count, not this field", or add a
   `plan_sample_count_reported` field if the observer must see the raw value.
5. **The refusal detail has no documented source.** Fields 41–43 are "refusal
   only" but §3/§10 do not say how the publisher learns `expectedSha256`,
   `actualSha256` and `reason` (the agent logs them in its
   `checkpoint_refused` error record). Implemented as a shell-level
   `SetRefusal(...)` call. *Proposed addition:* name the source (run record
   `checkpointSha256` vs the pinned identity, read at start-up, or the agent's
   error record).
6. **`PlanSample::heading` never reaches the wire** (unchanged from v1): the
   four arrays are acceleration, curvature, x, y; heading is derivable from the
   x/y sequence. Not a defect, just recorded.
