# SysML v2 API

API integration notes, clients, examples, and experiments.

## Role in DE4SDV

DE4SDV treats the SysML v2 API repository as the authoritative store for the
live model graph. GUI tools, viewers, analysis scripts, and automation should
interact with the model through the SysML v2 API instead of exchanging
uncontrolled model exports.

GitHub remains the authoritative reviewed project baseline. Generated textual
snapshots, rendered view artifacts, sync metadata, validation evidence, and
human-facing documentation are versioned in GitHub through pull requests.

See [ADR 0005](../docs/architecture-decisions/0005-use-sysml-v2-api-repository-as-live-model-store.md)
for the proposed live-repository decision.

## Pilot GUI tool

The initial GUI tool choice for the DE4SDV pilot is Eclipse SysON. The pilot
uses SysON as the preferred graphical editing environment for the live SysML v2
repository path while keeping the SysML v2 API boundary explicit so other tools
can be evaluated later.

SysON is currently treated as a pilot tool, not a mandatory production
dependency for contributors.

## Proposed sync loop

```text
SysON GUI edit or API tool edit
  -> export textual snapshot and rendered views
  -> update manifests with SysML/SysON project, document, view, and commit metadata
  -> open a draft GitHub pull request
  -> run repository checks and maintainer review
  -> merge to main
  -> privileged/import job updates the live SysML v2 API repository when needed
```

The sync pipeline must not push generated model updates directly to `main`.

## GitHub import loop

GitHub can still accept reviewed model-source changes. The direction is stricter:

```text
GitHub pull request
  -> public validation and maintainer review
  -> merge to main
  -> privileged/import job updates the SysML v2 repository
  -> import commit records the Git SHA
```

External contributors should not need model-repository write credentials or
private validation tokens to propose changes.

## Artifact ownership

- Live model elements: SysML v2 repository owns the current model graph.
- Reviewed baseline: GitHub owns the accepted public project baseline.
- Documentation and ADRs: GitHub owns the narrative and governance record.
- View definitions: GitHub owns DE4SDV viewpoint intent unless a future GUI
  workflow explicitly moves layout ownership to the model repository.
- Rendered view images: generated artifacts, regenerated by the sync pipeline.

## Production full-model ingestion

The primary runtime source is a validated import of the reviewed SysML baseline,
not fixture-created semantic objects. The import covers the textual model roots,
product models, and pinned source dependencies while excluding rejected snapshot
mirrors.

The pipeline has two explicit stages:

```bash
python scripts/export_sysml_api_baseline.py \
  --git-commit "$(git rev-parse HEAD)" \
  --output /tmp/de4sdv-full-model-export.json

python scripts/import_sysml_api_baseline.py \
  --api-url http://127.0.0.1:9000 \
  --export /tmp/de4sdv-full-model-export.json \
  --binding /tmp/de4sdv-full-model-binding.json \
  --report /tmp/de4sdv-full-model-semantic-validation.json
```

The export stage requires the official SysML parser/serializer and resolved
pinned dependencies. It records each source document and the source document of
every serialized UUID. The repository does not implement its own SysML parser.

The import stage preserves serializer UUIDs as API identities and reads the
created commit back. It fails closed if any element UUID or internal reference
is lost. References to objects outside the exported source set are removed from
the commit payload and listed explicitly in the export and semantic report.

The ontology report classifies every ontology class as `mapped`, `native`,
`external`, `unresolved`, or `ambiguous`. `mapped` requires one API UUID matching
the mapped source file, declaration name, and API metatype. `unresolved` and
`ambiguous` block a passed revision binding.

The privileged full-model workflow performs these stages against the exact
reviewed head, runs semantic queries across distinct concerns, and publishes the
binding and validation reports as review artifacts. Contributors who cannot run
the official native parser locally should use that workflow rather than create
an alternative parser.

## API query

API mode requires a binding record emitted by a validated import or fixture
run. It never silently queries a moving branch head.

```bash
python scripts/query_model_impact.py \
  --backend api \
  --binding /path/to/revision-binding.json \
  --json \
  reqCommandEmergencyBraking
```

The result contains:

- the root element and its resolution level;
- exact Git, project, commit, and element identifiers;
- ontology-to-kernel-to-API binding evidence;
- compact nodes and mapped edges with source URIs;
- semantic strength for each edge; and
- explicit model or integration gaps.

The AEBS query returns the requirement's member-product subject, three
relevant evidence contracts, and two verification cases. It intentionally
reports no architecture element because the reviewed model does not contain an
allocation from this requirement to architecture. It also reports that retained
evidence artifacts remain external. Those are trace gaps, not empty success
claims.

The existing text command remains the offline fallback:

```bash
python scripts/query_model_impact.py --backend text reqCommandEmergencyBraking
```

## Fast deterministic integration validation

Run a conforming SysML API service and seed the bounded AEBS fixture only for
fast transport and traversal tests:

```bash
python scripts/seed_aebs_api_fixture.py \
  --api-url http://127.0.0.1:9000 \
  --binding /tmp/de4sdv-api-binding.json
```

The seeder writes independent commits in dependency order because a repository
may assign new UUIDs. It reads each stage back, remaps references to the observed
UUIDs, and refuses to produce a `passed` binding unless the final graph contains:

- one exact requirement and member-product subject reference;
- three exact evidence contracts;
- two verification cases referencing those contracts; and
- three relevance dependencies targeting the requirement.

The fixture is a bounded integration asset backed by existing AEBS declarations.
It does not parse SysML text, does not claim to import the whole baseline, and
must not be used as the primary runtime source.

## Semantic boundaries

- A generic dependency is relevance only.
- Verification case references do not prove that verification passed.
- Evidence contracts define expected observations; they are not evidence
  artifacts.
- A missing modeled relationship is returned as a gap.
- An ambiguous identity is an error, not a best-effort match.
- A stale or unvalidated revision binding cannot be presented as the current
  reviewed baseline.
