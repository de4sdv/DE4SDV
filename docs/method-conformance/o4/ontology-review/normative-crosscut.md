## 2. Normative clause table — explicit form vs implicit semantics

|---|---|---|---|
| Typing (FeatureTyping) | KerML §8.3.3.3.7, p. 200 | `feature : Type` | FeatureTyping **is Specialization** with the feature as the specific Type: instances of the typed feature are a subset of instances of the type; a classifier type means the feature's values are instances of the classifier. Conformance only — no lifecycle, execution or evidence semantics follow from typing |
| Specialization / Subclassification | KerML §8.3.3.1.8 p. 166; Subclassification §8.3.3.2.3 p. 179 | `:>`, `specializes` | All instances of the specific type are instances of the general type (subset or equal set). Subclassification = Specialization between Classifiers |

| Redefinition | KerML §8.3.3.3.8, p. 200 | `:>>`, `redefines` | A kind of Subsetting requiring the redefined and redefining features to have **the same values** on the redefining feature's domain: restrictions (type, multiplicity) propagate in both directions |

## 3. Implicit-semantics conclusions (ranked)

1. **Typing/subclassing alone is representation-only for DE4SDV claims.** KerML §8.3.3.3.7/§8.3.3.2.3 give value-conformance only. An application `part def` (e.g. `StakeholderNeedCandidate` usage typed by the kernel requirement) gains no verification, allocation or lifecycle semantics from typing; it stays REPRESENTATION_ONLY unless a pattern witness (typed ends, doc claim boundary) is present.
2. **Direction discipline is normative, not stylistic.** Subsetting (§8.3.3.3.10) fixes value flow subsetting→subsetted; DE4SDV's canonical `derivesRequirementFromNeed` (Requirement→Need) is inverse traversal over the same witness whose native direction is Need→Requirement (`docs/method-conformance/k-slice/v11-final-decision.md:62-67`). Both directions must resolve the same modeled fact; end roles are identified by the end's own typing, never by end order or query direction.
3. **Allocation is structurally binary by norm.** "Always binary, having exactly two end features, even if abstract" (§7.15.2) — the binary-ness is a metamodel constraint, not an authoring convention; role intent must come from end typing, not position.
4. **Dependency carries no instance-level semantics** (KerML §8.3.2.2.2). A plain Dependency between identically-typed endpoints cannot be distinguished semantically from a stronger claim, so any DE4SDV strength claim must live in the pattern's declared claim boundary (doc), not in the Dependency itself. This is exactly the plan's adversarial case ("unrelated generic Dependency with identical endpoint types").
5. **Verification semantics are objective-scoped.** RequirementVerificationMembership lives in the VerificationCase's objective, owner=case, member=verified requirement (§8.3.24.2). Prior live-API observation: `verifiedBy` forward resolves the element IS the verification case, members are verified requirements, resolvable both ways on the deployed API (owner=case / member=requirement). `hasSubject` maps to the verification case's subject input parameter (UUT), not to arbitrary requirement subjects.
6. **Variation is implicitly abstract** and variant kinds are constrained to the owning variation's kind (§7.6.7) — relevant to PLE/configuration semantics, not to the 13 O3 identities; do not import variation semantics into verification identities.
7. **Viewpoint is a requirement kind** (§7.26.1/§7.26.3); view/concern chains are requirement-structure, so treating views as pure visualization representation undersells them; conversely, treat view artifacts as representation, not as claim witnesses.
8. **`SemanticMetadata` is sharply constrained.** Pinned/machine-readable Metaobjects: single `annotatedElement : Type` + `baseType : Type`; no separate `baseFeature`; a semantic-metadata usage is valid only where the annotated element may be a Type and `baseType` is bound so the implicit specialization/subclassification/subsetting effects are well-defined (plan line 100 and following normative paragraph). Reject "every user-defined keyword implies a specialization"; never use it as a generic relationship marker.
9. **The rejected `Derivation` library is a live example of implicit-semantics risk.** Its normative `originalImpliesDerived` constraint would make logical-implication/satisfaction part of the model regardless of runtime execution; the claim boundary wanted is provenance only, so the minimal application `connection def DerivesFromNeed` was chosen and the library stays pinned-but-unadopted (`docs/method-conformance/k-slice/v11-final-decision.md:18-51`; `textual-notation-of-model/packages/methods/de4sdv/de4sdv_method_context.sysml:25`).

## 4. Representation misconceptions to avoid

- **Export witness ≠ live API observable.** The VerificationCase grounding result proves "every governed element proves the implied library anchor edge **from the exact-revision export**" (grounding note). The refs are in the export's `external_references`: 44 def-role refs (22 sources × {`general`, `superclassifier`}) and 68 usage-role refs (34 sources × {`general`, `subsettedFeature`}), mechanism `external-reference`, provenance `implied`; direct element-level references to the anchors are 0. That is an export-level implied-edge anchoring, not a first-class imported-symbol API closure. The live API read-back (MCP validation artifact) is separate; do not equate the two or restate the export witness as a live API observable.
- **YAML parity ≠ authority.** The projection derives semantic fields from the validated model and loads YAML only as a parity oracle; drift fails generation (`v11-final-decision.md` Q2; `de4sdv/semantic/projection_v1.py`). But this is generation-time; it does not make the runtime authoritative — see §5.
- **Lock entry ≠ adoption.** "A lock entry is not adoption" (`representation-decision.md:63` per prior audit); candidate libraries must not be counted as accepted libraries.
- **Artifact publication never promotes support** ("vocabulary-only" retention across all 13 rows in the O3 support-preservation check).
- **Beta 1 citation drift** (§2 hazard) — stale clause/figure numbers silently mis-resolve against the formal texts.
